# 制作方法 · 五阶段 + 11 维评分卡

> 本包是"工厂"不是"方法论库"。方法论从你的 `skill-crafting`（技能匠人专家）继承精简版，重点在**可执行的验收门禁**。当你未选中该专家时，本文件作为兜底制作规范。

## 五阶段

### 阶段 1 · 需求澄清（六要素）
先把模糊诉求收敛成六要素，输出需求确认（**不代表同意写入**）：
1. **做什么**：一句话定义这个 Skill 的职责边界。
2. **谁用**：你自己 / 团队 / 公开受众。
3. **输入**：口述流程、提示词、旧目录、还是脚本片段？
4. **输出**：完整目录 + ZIP + 质检报告？
5. **边界**：该触发 vs 近邻不该触发（给 2-3 个近邻反例）。
6. **绝不做什么**：明确红线（不覆盖、不删文件、不写凭据……）。

### 阶段 2 · 调研与查重
- 扫 `~/.workbuddy/skills/`（已装 14+）、工作区技能目录。
- 用 `marketplace search <关键词>` 查 WorkBuddy 推荐市场是否已有同类。
- 命中同名/同义 → 提醒用户，避免和你 `Zero-WYM-*` 生态撞车。

### 阶段 3 · 设计
- 定名：`Zero-WYM-<短名>`，与现有同族并列。
- 写 `description`：自然嵌入用户**实际会说的短语**（路由靠它）。
- 定脚本边界：哪些环节能脚本化（结构校验/触发评测/密钥扫描/安装/发布），哪些只能文档化。
- 定 `evals/trigger_cases.json` 三桶用例。

### 阶段 4 · 实现（零依赖）
- 所有 Python 脚本**仅用标准库**（`os/sys/re/json/shutil/pathlib/subprocess/argparse`）。
- 不 `import yaml`；frontmatter 用包内自写解析器。
- 每个交付文件必须**完整可用**，不写 TODO 占位。
- `SKILL.md` ≤ 14KB（上下文预算）。

### 阶段 5 · 验收（量化门禁）
跑 `check_env` → `validate_skill` → `trigger_eval` → `secret_scan` → `install_skill`。任一红灯回到阶段 4 修正。**未实跑不报通过。**

## 11 维评分卡

| # | 维度 | 通过标准 | 检查手段 |
|---|---|---|---|
| 1 | 命名 | `Zero-WYM-` 前缀、无歧义、不与已装撞车 | 查重扫描 |
| 2 | 触发词 | `description` 含用户真实说法、路由可达 | `trigger_eval` + 人工 |
| 3 | 结构合规 | SKILL.md 存在、frontmatter 合法、无嵌套 SKILL.md | `validate_skill` |
| 4 | 体积预算 | SKILL.md ≤ 14KB | `validate_skill` |
| 5 | 脚本零依赖 | 仅标准库、可独立运行 | `check_env` + 静态导入检查 |
| 6 | 密钥安全 | 零命中 | `secret_scan` |
| 7 | 文档完整 | references 覆盖方法/评测/发布/平台约定 | 人工 |
| 8 | 用例可跑 | `evals` 三桶齐全、`trigger_eval` 能加载 | `trigger_eval` |
| 9 | 边界清晰 | 该触发/近邻不误触分离明确 | `trigger_eval` 近邻桶 |
| 10 | 安装安全 | 备份+原子替换+回滚路径存在 | 实跑 `install_skill` |
| 11 | 可维护 | 无 TODO 占位、逻辑自洽、注释到位 | 人工 |

> 评分输出形式：每维 通过/注意/失败 + 一句证据。汇总成质检报告末节的"11 维评分"。
